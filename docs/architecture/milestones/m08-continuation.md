## Task4 orientation contract

The standalone display transform is independent of Task3 and is implemented while detail-stage and executor preflight run. `OrientationTransform` accepts explicit image layouts, display storage and bounded byte spans, reports a tight output layout, and maps both Gray8 and Gray16 by exact integer coordinates. It applies horizontal flip, vertical flip, then clockwise rotation. Quarter-turns swap dimensions. Identity directly copies to a distinct destination; the executor can bypass it for an identity installation profile.

All validation precedes writes: supported rotation/storage pair, expected output dimensions, complete spans and no complete-payload aliasing. Odd strides and unaligned Gray16 samples are valid; only active sample bytes are copied. Input, padding and canaries remain unchanged. Stable `orientation_*` errors identify failures. No OpenCV dependency or heap allocation is needed on the successful transform path.

Task5 integrates the same immutable stopped-state orientation into both display routes and prepares the required display layouts/pool leases. Native RawFrame and enhanced U16 storage stay untouched. No new live orientation control or administrator profile UI is added in Task4.

## Task3 detail contract

Gaussian denoise gains trailing `sigma` with default zero (automatic coefficients); accepted explicit sigma is finite [0,5], kernels3/5/7. Median accepts kernels3/5 and sigma zero. These bounds are now explicit configuration decisions, not previously specified PRD values. Both direct factories and compiler enforce them.

All neighborhoods use REFLECT_101, including singleton dimensions. Pinned OpenCV prepares double Gaussian coefficients; Lumora performs separable convolution with a prepared double intermediate and one final U16 round. Median selects the middle of a fixed9/25-sample reflected neighborhood. These locally owned execution paths remove per-call backend allocation routes. Gaussian output is defined by this double-kernel calculation and can differ from OpenCV's quantized U16 Gaussian output; analytical references and future designated-platform comparisons must reflect this provenance.

Sharpen radius is sigma, kernel is `2*ceil(3*radius)+1`, blur is rounded once to U16, detail is signed original-minus-blur, and only absolute detail strictly above threshold contributes. Final output saturates and rounds positive halves upward. Amount0 and threshold65535 are exact copy paths after normal validation. Existing parameter bounds remain unchanged.

Prepared stages own scratch through an explicit factory/PImpl and belong to one sequential processing worker. This replaces the earlier plan's unavailable workspace-scratch access; the executor owns their lifetime and budgets their exact requested bytes. Gaussian/sharpen each retain one width×height double image and a bounded coefficient array. Median retains no full image scratch. Factories accept a configurable scratch budget (default256MiB per standalone stage); Task5 applies a separate complete resource budget and accounts for active/candidate/retired owners. No successful process call resizes storage or constructs a kernel.

The allocation gate for M8 measures processing of a preexisting immutable RawFrame through output FrameBundle publication and release, including metadata/control blocks and stage work. Acquisition-side metadata construction is a separate scope and will not be described as allocation-free by that measurement. Designated Windows reference/workstation acceptance remains pending external evidence; locally implementable allocation debt is not deferred to that gate.

## Task5 execution and resource decisions

Task5 is divided into four reviewable implementation slices: (5A) pooled output metadata and fixed timing records; (5B) bounded prepared CLAHE execution; (5C) complete activation/execution, resource admission, shared orientation and enhancement-failure fallback; (5D) canonical Standard, deterministic reference tooling, allocation verification and benchmark JSON. This sequencing preserves working ownership and algorithm tests while exposing failures at a small boundary.

Output metadata keeps the existing shared_ptr<const Frame> API. A prepared FrameObjectPool provides separate typed object slots and control-block slots, with runtime discovery of the standard library's actual allocator-rebound control shape. Weak references retain their old control slot until release; they never observe a reused object generation. Pool state outlives the engine whenever displayed/captured/weak owners remain. Existing allocating frame factories stay available; the engine uses new pooled overloads. Exhaustion never falls back to heap frame storage. Successful timing records use sixteen inline entries with owned identifiers of at most63 bytes; checked append rejects overflow or invalid names without truncation.

An opaque immutable FrameObjectPoolPlan performs only bounded control-shape probes and computes storage requirements. Bulk pool creation consumes that same plan after aggregate admission; it does not allocate capacity-sized slabs merely to discover their size. Reported required storage includes aligned object/control slabs, requested free-list/bookkeeping storage and documented fixed state. Probe and allocator overhead coverage is explicit.

The CLAHE wrapper's public contract and U16 references remain, but Task5 replaces its per-apply OpenCV state with a prepared CPU implementation of the pinned histogram clipping, redistribution, reflection and interpolation arithmetic. It retains a LUT, one sequential histogram and bounded interpolation/reflection indices. No OpenCV scheduler/backend call runs per frame. Any copied upstream implementation retains its license/copyright and provenance. Compatibility is established by analytical cases, the existing fixture and targeted comparisons, not asserted from intent. This resolves the known allocation gap rather than treating it as an external Windows gate.

Prepared CLAHE preserves pinned float saturation using the private inline OpenCV helper. Preparation and execution require the normal `FE_TONEAREST` rounding environment; another standard rounding mode is rejected before scratch or output writes, without changing the caller's environment. Its image-count scratch trait becomes zero after removing the bridge images, while an explicit byte estimator still accounts for LUT, histogram, interpolation and reflection arrays. Resource admission must use those bytes.

The default safe preparation budget is512MiB of explicitly accounted Lumora resource storage, configurable at engine/session preparation. It includes aligned pixel pools, output object/control slabs, orientation scratch, stage buffers and bounded configuration/activation reserve. It is an admission budget, not total process RSS or a promise about operating-system/dependency memory. Required bytes and the selected limit are exposed before streaming; impossible arithmetic or an insufficient limit rejects preparation before acquisition. Candidate configuration preparation is serialized; executable snapshots stay private, with at most active, candidate and one in-flight retired configuration. Resource accounting must cover retained stage state and last-gamma cache without unbounded historic caches.

Candidate immutable stage configuration may be prepared on the calling control thread using separate owned resources while the worker processes its prior snapshot. Publication is atomic after successful validation/preparation. This clarifies earlier stopped-stage wording: existing scratch/pixel pools are never resized by process or concurrent activation; source extent/storage, orientation and session resource-envelope changes still require stopped-state replacement. Shared unchanged stage handles are accessed sequentially by the single worker; preparation must not warm or mutate an active backend. Unchanged gamma retains one cached table across unrelated revisions and disable/re-enable; changed gamma creates a new table before publication.

Preparation reserves a fixed configurable per-activation storage envelope for each of the three possible executable owners. Its automatic default divides the remaining session budget by three after subtracting fixed storage and the bounded gamma-cache reserve, with checked arithmetic. This is reserved admission headroom, not a claim that all reserved bytes are resident or allocated. A live candidate exceeding the envelope is rejected before allocation and leaves the active configuration intact; increasing the envelope requires stopped preparation. Diagnostics expose fixed storage, the three-owner reserve, candidate requirements and the selected limit.

The budget covers one prepared session. Immutable displayed or captured frames may retain pools from prior sessions beyond this envelope; the limit is not a bound on all outstanding sessions or total process memory. Cross-session retention policy remains unchanged.

Execution preserves canonical subsequences accepted by M7; the default registry and Standard definition contain all eight canonical entries. Normalize into A, evaluate Original window/level into B, map Original before overwriting B, then ping-pong Enhanced through enabled stages. Missing WindowLevel retains the established identity Original mapping. Disabled Enhanced stages are not invoked; Original-only WL work is counted separately. Both display routes receive the same immutable orientation; native raw and Enhanced U16 stay unchanged. Nonidentity orientation uses one dedicated native display temporary reused sequentially and counted separately from publishable pool leases.

After three consecutive enhancement failures, publish valid Original-only output and retain a non-modal warning until a valid new configuration or explicit processing retry is consumed. The first two failures discard their processed frames; successful enhancement before the threshold resets the consecutive count. A partial Enhanced image is never published. Failure of normalization, Original WL/map or orientation cannot supply a valid fresh Original; it drops the frame and leaves existing stale indications truthful. Structured processor status must preserve the latched warning through Original-only success instead of letting the worker clear it as ordinary enhancement recovery. Deterministic stage-failure/invocation testing uses a narrow internal factory/dispatch seam.

Enhanced-only terminal map/orientation faults join that threshold after Original is complete; Original-route faults cannot publish fallback. Intervening resource/source/Original faults neither increment nor reset the count of failed enhancement attempts. A warning-local Retry enhancement button sends a coalesced, generation-checked processing intent consumed at a frame boundary. It does not reconnect the camera or introduce the M9 configuration editor, and its warning coexists with existing pause/stale status.
